# API design

**Status:** M5.0–M5.4 development is complete for isolated local testing with synthetic data. Option A approval covers the limited-pilot design. External staging and processing real data require separate approval. [Local evidence and open gates](../../PLANS.md#m5-operational-and-acceptance-gates)

The API uses account-scoped opaque bearer sessions. HTTPS is required for external deployment. The isolated Android debug fixture uses fixed loopback HTTP through ADB forwarding. Room remains authoritative. Cloud routes run only on explicit account, backup or recovery actions. Manual SAF backup and restore continue to work offline without an account. API v1 and portable snapshot format v1 are independently versioned.

## Accounts and sessions

Auth responses use `Cache-Control: no-store`. JSON control bodies have an 8 KiB limit and reject unknown or duplicate fields. Use a canonical lowercase ASCII username proposed at 3–32 characters, drawn from letters, digits, dot, underscore and hyphen, and a password proposed at 15–128 Unicode code points without truncation or silent normalization. Return UTC ISO timestamps. Account IDs are server-generated UUIDs. Token and code fields are strings. The server derives ownership from an active session on every protected operation. No route accepts a client-selected owner or storage path.

| Method and route | Request | Success |
|---|---|---|
| `POST /v1/auth/register` | `{inviteCode, username, password}` | `201` with `{accountId, sessionToken, sessionExpiresAt, recoveryCode, recoveryExpiresAt}`. Consume the invite and create the account, session and recovery verifier in one transaction. |
| `POST /v1/auth/login` | `{username, password}` | `200` with `{accountId, sessionToken, sessionExpiresAt}`. Issue an independent session per sign-in. |
| `POST /v1/auth/recover` | `{username, recoveryCode, newPassword}` | `200` with the registration response shape. Consume the code, replace the password, revoke all previous sessions and issue a replacement code and session atomically. |
| `POST /v1/auth/recovery-code` | Bearer and `{password}` | `200` with `{recoveryCode, recoveryExpiresAt}`. Fresh credential check, then atomically replace the previous code. |
| `POST /v1/auth/logout` | Bearer | `204`. Revoke the presented session. Android’s explicitly zero-length POST can carry a media-type header. A logout payload remains invalid. The app clears the local credential even offline. An unreachable server cannot revoke that token until expiry or a later account-wide revocation. |
| `DELETE /v1/account` | Reserved for M6 | Fresh credential check, remove account access and active snapshot, revoke sessions and record deletion durably. Local erasure remains a separate control. |

**Credential policy for M5.1.** A named pilot operator issues one-use invites with 128 bits of CSPRNG entropy and a seven-day expiry and can revoke unused invites. Issue 256-bit random session tokens with a 30-day absolute expiry and no refresh token. Generate 128-bit random recovery codes with a 365-day expiry, one active code per account, and display them only at issuance. Encode codes to be copied and saved offline, with unambiguous entry and an exact normalized representation. Store only SHA-256 verifiers for random tokens and codes. Salt password hashes individually and use Argon2id. Benchmark work factors and bound concurrent verification on the intended host. Use generic credential failures and equivalent bounded work for unknown usernames. [Argon2id guidance](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)

Key the rate limiter by route and pseudonymous source, with additional normalized username buckets on login/recover and account buckets for authenticated actions. Starting limits are 10 unauthenticated attempts per source per minute and 5 login/recovery attempts per username per 15 minutes, with global work limits and no permanent lockout. Starting upload limits are 20 requests per account per hour plus 1 concurrent PUT body per account and a global memory budget. Return `429` with `Retry-After`. Test distributed guessing and shared-network behavior before rollout. Trust forwarded source addresses only through the configured ingress.

Check time, revocation, account state and relevant credential version in the same serialization boundary as each protected mutation. A pending upload cannot commit after recovery or deletion has won that boundary. A read authorized before revocation may already have returned data. A replacement device can sign in with the existing password or reset it using the saved code. If registration or recovery committed but the response was lost, sign in with the submitted password and rotate the unread code. Client-side encryption separately requires the snapshot key.

**Ledger binding.** Confirm first binding to the authenticated immutable account ID before allowing upload. Persist this binding across sign-out and retain only an account-scoped credential for the signed-in session in Keystore-protected, non-backed-up storage. Signing into another account never reassigns a populated ledger, carries pending bytes across accounts or reuses its revision. Require an independently empty ledger for a new binding, or a separate approved data-removal/reset workflow. Confirm the target account for replacement-device restore. Serialize binding and cloud restore in the client so an account switch cannot race a commit. Logging, reporting, reminders and manual SAF remain available signed out or offline.

The M5.1 implementation uses lowercase hex tokens and codes, with SHA-256 verifiers for the issued random values. Argon2id uses 64 MiB, three passes, four lanes and a random 16-byte salt. Local per-process concurrency is capped at two password operations. Throttling persists in PostgreSQL across app processes that share the same HMAC key. The local implementation caps the route-specific source at 10 requests per minute, keeps a shared login/recovery bucket of five per username per 15 minutes and caps all auth requests at 60 per minute. Recovery-code rotation also has a five-per-15-minute account bucket. The loopback server ignores forwarded IP headers. [Local operation](../../server/README.md)

## Snapshot requests

Backup responses use `Cache-Control: no-store`. Use opaque, strong, nonrepeating slot revisions, including on an empty slot. Do not derive revisions from the payload digest or reuse a revision after replacement, expiry, deletion or operational restore. On `/v1/backup`, `ETag` is the quoted revision. `If-Match` compares one exact quoted revision. Wildcards and lists are invalid. The empty-slot revision is discoverable through metadata and is valid only while that empty state is current. Use server time for expiry. M5.2 requires an explicit synthetic-only lifetime and the loopback development script uses one hour. Metadata, download and PUT materialize expiry and its new empty-slot revision once under the account lock. A deployed retention and scheduled purge policy still requires approval.

**Metadata model**

- Slot metadata is `{slotRevision, snapshot}`. `snapshot` is null for an empty or expired slot.
- Snapshot metadata is `{attemptId, acknowledgedAt, expiresAt, byteLength, sha256, payloadFormat}`. The attempt ID is a client-generated lowercase UUID, the times are UTC ISO strings from the server, the length is a nonnegative integer, and SHA-256 is lowercase hex over the exact stored wire bytes. Proposed payload formats are `snapshot-v1` for A and `encrypted-snapshot-v1` for B. Deploy only the approved format.
- Encrypted storage in A retains the original JSON bytes at the API boundary. B retains the exact uploaded envelope, with the original JSON bytes recoverable after authenticated decryption. Digests detect byte mismatch and do not replace TLS, authorization or authenticated encryption.

| Method and route | Request | Success |
|---|---|---|
| `GET /v1/backup/metadata` | Bearer | `200` with slot metadata. Empty and expired slots return `snapshot: null`. |
| `PUT /v1/backup` | Bearer, required `If-Match`, required `Idempotency-Key` UUID, `Snapshot-Format`, and original bytes as the body. | `200` with the committed slot metadata and `ETag`. The same accepted attempt for a still-current revision returns the original acknowledgement. |
| `GET /v1/backup` | Bearer and required `If-Match` from the populated metadata the user chose to restore. | `200` with the exact stored bytes, `ETag`, `Content-Length` and `Snapshot-Format`. Return `404` if no current snapshot exists, or `412` if another populated revision replaced the selected one. |

Use UTF-8 `application/json` in A and `application/octet-stream` in B. Accept identity content encoding only. Reject a known oversize body at ingress and count streamed bytes regardless of the declared length. The plaintext limit is 4,194,304 bytes. In A apply the full [portable v1 validation contract](DATABASE_DESIGN.md#portable-snapshot-format-v1), including the same parser and collection budgets, references and ledger invariants. Validate integers from original decimal tokens within signed 64-bit bounds. Store raw bytes as PostgreSQL `bytea` and avoid a JSON reserialization step. Option B is outside the implemented API. In B the proposed outer cap is 4,194,560 bytes, providing up to 256 bytes for fixed framing. The server checks the approved envelope version, framing and bound account and attempt IDs. Only the phone can authenticate/decrypt and fully validate the inner snapshot. Incompatible or corrupt inner payloads fail locally before import.

### Upload and retry

1. Capture a consistent Room snapshot only after explicit action. Preserve the exact bytes, account, binding, base revision and attempt UUID in app-private excluded storage. Check that the base is either the confirmed empty slot or the last known acknowledged revision the driver explicitly chose to replace. Metadata refresh after a conflict must not silently rebase a pending write.
2. Enforce transport bounds and validate control headers, then compute the payload digest and validation result before taking the write lock. Under the account lock, recheck session and account state, transition any expired slot, then resolve any retained attempt receipt before testing the precondition or returning a payload validation error. The receipt stores the base revision, result revision, digest, length, format and acknowledgement metadata alongside the attempt UUID. The local receipt TTL is seven days and the cap is 256 live receipts per account. Throttle new accepted writes at the cap until a receipt expires. Receipts hold no historical payload. Apply the account's rate limits separately.
3. Match an existing receipt against the original base revision, format, length and digest. Mismatch returns `409 attempt_mismatch`. If the matched result is still current, confirm exact byte equality against the stored body and return the original acknowledgement, even though `If-Match` is now stale. If the result was replaced or expired, return `409 attempt_superseded` and require a fresh explicit operation. Receipt expiry ends replay recognition, and the unchanged old precondition still cannot commit. Generate a fresh attempt ID for every new upload. A superseded or expired receipt never returns payload bytes.
4. For a fresh attempt with a valid payload and a matching precondition, commit the new payload, revision and receipt in one PostgreSQL transaction. Send success only after commit. Two different attempts against the same base revision produce at most one committed replacement. The losing device keeps its ledger and can inspect the cloud state or retain a manual copy. Overwriting after a conflict requires separate informed confirmation and a fresh attempt against the observed revision.
5. If the response is lost, show an unconfirmed outcome. On explicit retry send the original request. If confirmation returns, record the server's acknowledgement for the captured snapshot and explain that later edits still require backup. If another write superseded it, show the current cloud state separately. Never infer success solely from matching timestamps or a network timeout.

## Error semantics

Errors use `{error: {code, requestId}}` and fixed client-localized messages. Never reflect credential values, usernames, row data or payload text. Authenticated GETs and writes resolve the same account-owned slot. Malformed or unknown auth and snapshot format details are reported only within their appropriate authenticated context.

| HTTP | Stable codes and handling |
|---|---|
| `400` | `invalid_request` for malformed control fields or validators. |
| `401` | `invalid_credentials` for unknown account, invalid or expired invite/code, or wrong password. `invalid_session` for missing, expired or revoked bearer. Prompt sign-in only where appropriate. |
| `404` | `snapshot_missing` for an empty or expired download target. |
| `409` | `registration_conflict` for username unavailability only after a valid invite. `attempt_mismatch` for reused attempt with changed inputs. `attempt_superseded` for a matching attempt whose result is no longer current. |
| `412` | `revision_conflict`. Refresh metadata on explicit request and preserve local data. |
| `413` | `body_too_large`. No partial write. |
| `415` | `unsupported_media_type` for media type or encoding. |
| `422` | `snapshot_invalid` for malformed payload or violated constraints. `snapshot_incompatible` for unsupported format version or currency. |
| `428` | `precondition_required` for missing `If-Match`. |
| `429` | `rate_limited` with `Retry-After`. |
| `500` / `503` | `internal_error` / `temporarily_unavailable`. Treat interrupted or errored writes as unconfirmed and retry with the same captured request when the driver chooses. |

## Android restore

1. Show acknowledged metadata for the confirmed account. Ask the driver to confirm restoring that revision into the empty local ledger. Preflight all ledger tables for emptiness and pass the chosen revision to the download.
2. M5.4 stages bytes only in private process memory. A valid response has the chosen ETag, format, JSON media type, identity encoding and declared length matching metadata, within the inclusive 4 MiB cap. Verify the actual length and SHA-256 before decoding. Release the buffer after each attempt, including failure, and keep no restore request or payload across process death. For B, authenticate and decrypt the envelope within the plaintext cap. B remains outside the implemented API.
3. Use the existing strict v1 codec and shared SAF restore transaction. After validation, request metadata again to recheck the authorized revision and reject a revoked session or replacement. Serialize the flow with local account operations and recheck the original session, binding, and snapshot expiry inside Room before the authoritative four-table emptiness check and inserts. The server recheck and local transaction are separate system boundaries. A server change after the final response cannot invalidate already-authorized local bytes. A local writer that wins the Room transaction makes restore fail without modifying the new records.
4. Reset stale local notification delivery state and reconcile schedules only after successful commit. Record the revision in Keystore-backed local state separately from upload acknowledgement. Cleanup or receipt storage failure produces a restored-with-warning result. If the process dies before recording the receipt, the committed Room population still blocks repeat restore. The existing filesystem and database boundary allows a hard process death immediately after commit to interrupt notification-marker cleanup. Local logging remains available independently of cloud state.
5. A replacement installation can sign in with the existing password or redeem a saved one-use recovery code under the account contract. The reset replaces the password, revokes old sessions, and shows the new recovery code once. Explicitly bind the empty local ledger to the account and review server metadata before confirming a download. Both sign-in paths work with the existing loopback-only opt-in debug fixture.
