# ADR 0004 · Cloud recovery security and custody

**Status:** Option A approved for the limited pilot. External deployment and real personal data require separate approval. The lifecycle proposals below remain provisional.

**Context:** Room remains authoritative. Logging and manual SAF backup and restore work without an account or network. The invite-only cloud service stores one current snapshot per account following an explicit upload. Both restore paths require a completely empty ledger. Automatic upload, background sync, live sync and merge are out of scope. The snapshot contains potentially personal data, including free-text vehicle labels, notes and reminder titles alongside financial and maintenance records. See the [portable format](../DATABASE_DESIGN.md#portable-snapshot-format-v1) and [proposed API](../API_DESIGN.md).

## Options and consequences

| Question | A. Server-readable over HTTPS with encrypted storage | B. Client-side encryption with a driver-held key |
|---|---|---|
| Original phone lost | Sign in or recover the account, then explicitly restore to an empty ledger. | Sign in or recover the account, then enter the separately saved snapshot key on the replacement phone. |
| Recovery and custody | Driver keeps the single-use account recovery code off-device. Approved infrastructure and named operators control storage and backup encryption keys. The live service can read the payload. | Driver keeps both an account recovery code and a distinct high-entropy snapshot key off-device. The phone protects its copy with Android Keystore. Infrastructure keeps its own storage encryption and never receives the snapshot key. |
| Account takeover | A valid stolen session or successfully recovered account can read and replace the current snapshot. Revocation stops later requests. Bytes already disclosed cannot be recalled. | A compromised account can download ciphertext and replace the current snapshot with unusable or attacker-controlled bytes. Plaintext disclosure additionally requires the snapshot key or a compromised authorized endpoint. |
| Confidentiality and verification | HTTPS protects transit and encrypted storage protects raw media. The application, an authorized operator or a compromised server can access plaintext. The API can validate the full codec before acknowledging. | The service sees account, timing, size and envelope metadata. The client must validate before encryption and after authenticated decryption. A server acknowledgement covers storage of the envelope. A malicious service can withhold or replay an older valid envelope, especially on a fresh installation. |
| Solo developer and support | One validation pipeline on each side. Operational responsibility includes restricting privileged access and responding to plaintext exposure. | Adds a format, cryptographic review, recovery-key onboarding and support, and tests for key loss, mismatch, tampering and envelope migration. Account takeover can still destroy availability because there is one slot. |
| Recurring cost | API compute including password hashing and validation, private database, encryption and key service as applicable, backups, transfer, monitoring and operator time. | Same base categories, small envelope overhead, and more recovery support and client review time. Server payload validation cost is lower. Both options need staging and restore drills. |
| Recovery secrets lost | An accessible password can authenticate and rotate the recovery code. If both password and valid recovery code are lost, the proposed policy offers no operator bypass. Local data and any manual export remain usable. | Same account policy. Loss of every copy of the snapshot key makes the ciphertext unrecoverable even after account recovery. Restart with a new key only from an existing local ledger or retained export, with explicit confirmation that a new upload replaces the prior slot. |

Option A is the recommended default for a small supported pilot **if** the product owner approves the plaintext-access threat and the operator controls. Option B is appropriate if confidentiality from the service or its operators is a product requirement. In B, validate the existing v1 plaintext on the phone and use a reviewed, versioned authenticated-encryption profile. The proposal uses a random 256-bit driver-held recovery key, a fresh random salt per upload to derive a per-upload subkey with HKDF-SHA-256, and AES-256-GCM with a fresh 96-bit nonce and 128-bit tag. Authenticate the envelope version, account UUID and attempt UUID as associated data. Confirm the off-device recovery key before enabling the first upload. Retry the original ciphertext bytes. Preserve the manual SAF plaintext export format. Finalize the binary layout, key encoding and lost-key replacement flow in a crypto review before implementing B. [HKDF](https://www.rfc-editor.org/rfc/rfc5869.html) · [Authenticated encryption and AES-GCM](https://www.rfc-editor.org/rfc/rfc5116.html)

Authentication grants time-limited account access. Account recovery rotates account credentials and revokes existing sessions. Snapshot decryption in B requires the independent snapshot key. Passwords, sessions and recovery codes cannot derive or reset that key. In A decryption is an infrastructure responsibility.

## Threat model

| Threat | Control and remaining exposure |
|---|---|
| Cross-account request or account switch | Resolve ownership from the bearer session on every request. Bind local attempt bytes and metadata to the confirmed account and ledger. Retest account, binding and local emptiness before committing an import. |
| Stolen phone, session, password, invite or recovery code | Protected local storage, expiration, revocation and single-use code rotation limit future access. Possession of a valid bearer or unredeemed recovery code can still confer account access. Prompt off-device secret retention without logging or analytics. |
| Server, database or operator compromise | Private database, least privilege, encrypted storage and backup, audited break-glass access, and named credential custody. A exposes content to a compromised running service. B protects contents while key and client remain uncompromised. Neither prevents deletion, withholding or metadata exposure. |
| Replay, racing uploads or lost response | Account-scoped attempt receipts, revision preconditions, atomic replacement, and immutable retry bytes. A conflict preserves the current server snapshot and the local ledger. |
| Malformed payload, resource exhaustion or interrupted restore | Bound body size, parsing, auth work and time. Verify integrity and validate before the Room transaction. Recheck emptiness inside the transaction. No partial restore. |
| Deleted data reappearing after an operational restore | M6 reconciles a separately retained deletion ledger and snapshot expiry before reopening restored service. Revoke pre-restore sessions and invalidate outstanding invites and recovery codes that cannot be proven current. Check revision reuse and old pending uploads. |
| Reachability, operator error or loss of all recovery material | Manual backup and offline logging remain available. Service availability, off-device secret retention and all recoverable data are limited by the retained snapshot and backup policy. |

## Proposed lifecycle and operations

- Store the current payload and baseline metadata in private PostgreSQL. Limit roles to application, migration, backup and explicitly authorized support operations. Encrypt disks, replicas and backups using approved keys and custody. Keep the database off the public network. Run the app API over authenticated HTTPS. Use independent credentials and databases for each environment.
- Replace the current payload atomically and give the new revision its own acknowledgement time and expiry. The recommended starting policy is **90 days from acknowledgement**, with read access blocked at expiry and a purge job completing within **24 hours**. Reads and idempotent retries do not renew retention. Expiry never deletes local Room data or a retained manual file.
- Recommend encrypted off-host backups, including any provider point-in-time recovery logs, with **14-day maximum retention** from creation. Replacement, expiry and M6 deletion remove active access. Older data can remain in protected backup copies until they expire, including a copy taken during the operational purge window. Verify actual provider schedules and deletion behavior before promising these windows. Backup copies are for operations, with no user-facing version history. Warn users about both the active expiry and backup tail.
- M6 retains account deletion, separate local erase, the operational deletion ledger and the restore drill. Proposed account deletion requires fresh credential verification, revokes sessions and removes the active snapshot and account access under the same account lock used for PUT. Keep minimal deletion records in a separately durable store for longer than the oldest recoverable backup, including restore lag. Reapply deletions and expiry to a restored database before accepting traffic. Renew slot revisions after disaster recovery so pre-incident upload preconditions cannot succeed against a rolled-back state. A standalone cloud-snapshot deletion endpoint is outside the proposed M5 scope. Approve its ownership or an interim erasure procedure before any real personal data is accepted. Use synthetic staging data through this gate.
- Store only account identifiers, credential verifiers and state, slot metadata and bounded receipt metadata necessary to operate the service. Use random request IDs, route templates, response categories, duration and coarse size metrics. Exclude usernames, secrets, full IPs, payloads, digests and user text from persistent logs, including proxy and crash logs. Default proposal is 14 days for redacted logs. Use short-lived keyed rate-limit buckets for network origins. Restrict authorized access and record privileged actions.
- For suspected storage or credential compromise, disable affected access and writes, preserve minimally necessary incident evidence, assess which credentials and data were exposed, and revoke sessions and rotate affected credentials, keys and outstanding invites as appropriate. Suspend or reset recovery credentials if their state cannot be trusted. Coordinate investigation, driver communication and any required notification with the approved owner and privacy process. Reopen only after isolating the cause, reconciling deletions and expiry, restoring from a verified clean copy where needed, and auditing access.

## Approval and cost gates

| Decision needed | Recommended starting point |
|---|---|
| Data consent and allowed content | Option A is approved for the limited pilot. Disclose visibility, snapshot content, expiry, consequences of secret loss and the continued SAF option. Confirm data jurisdiction and handling of personal data before staging real data. |
| Invite and credential custody | Named pilot operator issues and revokes invites. Driver retains recovery material. No discretionary support resets or account rebinding for a nonempty ledger. Approve lost-secret instructions, test account reset procedures and the proposed session and recovery lifetimes. |
| Lifecycle and incident policy | Approve the 90-day snapshot, 24-hour purge, 14-day backup and log proposals, support responsibilities, deletion path and incident owner. Keep M6 delivery ownership. |
| Dependencies and infrastructure | Approve exact production dependencies and licenses before implementation. Approve host, region, private database, secret/key custody and rotation, reachability from target networks, spend ceiling and named operators before provisioning. No provider is selected. |
| Operating budget | Estimate API CPU/RAM and uptime, managed or self-run PostgreSQL and disks, replicas if required, backup/PITR storage and restore traffic, bandwidth, DNS/TLS, key management, monitoring/incident response and support time. Size active payload storage at up to 4 MiB per occupied slot plus framing in B, database overhead, receipts and backup amplification. Estimate using the invited cohort, upload/download volume and provider quotes after approval. |

**Disposition:** The product owner authorized M5.1 under the account contract with isolated PostgreSQL and synthetic accounts. M5.1 and M5.2 passed on disposable local PostgreSQL 18.7 fixtures. M5.2 implements Option A with an explicit synthetic-only lifetime and request-driven expiry. Provider, cost and personal-data approvals separately gate external staging or real-data use. The proposed 90-day snapshot expiry is unapproved for real data. M5.1 implements neither snapshot retention nor operational backup expiry. M5.0–M5.4 development is complete for synthetic loopback testing. The [operational and acceptance gates](../../../PLANS.md#m5-operational-and-acceptance-gates) remain open.
