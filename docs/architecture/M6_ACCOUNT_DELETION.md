## Proposed deletion module

Use the existing account authorization and transaction module. Snapshot reads and writes already acquire the account row lock and recheck the bearer. Login rechecks the credential version under that lock. Recovery redemption acquires the same account row lock. The deletion module should reuse these checks and concentrate the purge and replay behavior behind one interface so the endpoint and restore adapter exercise the same semantics. The current foreign keys do not cascade and the app role lacks the needed delete grants. Design a narrowly privileged purge path rather than granting general administrative access.

1. After authentication and explicit confirmation, serialize deletion under the account lock. Make an independently durable journal append the point of no return, then purge all account-owned rows in one PostgreSQL transaction. If journal or transaction outcome is uncertain, hold service closed until journal verification and replay. The design must guard active requests during uncertainty and check the journal on startup and before reopening a restored database. A fault between append and commit requires replay, and a failed append must never produce a success response. The two stores do not share a transaction.
2. Remove retry receipts before the snapshot slot, then remove sessions, recovery-code records, the redeemed invite bound to the account, and the account including password verifier and credential version. The redeemed invite must never become redeemable again. Preserve unrelated invites and other accounts during live deletion. Leave shared opaque authentication rate-limit buckets on their existing expiry path so deletion cannot reset abuse budgets. Android Room and retained manual exports are outside this operation.
3. A request that loses the account lock race must fail authorization or recheck before returning data or issuing a credential. A credential minted by a request that won the race is invalidated by deletion. Bytes already handed to a previously authorized response cannot be recalled. The current contract has no refresh endpoint or refresh tokens. Test login issuance and authenticated recovery-code rotation, and verify that there is no refresh route.
4. Restore the older database in isolation. Verify the journal's completeness against independently retained evidence, replay deletions idempotently by immutable account UUID, reap expired snapshots, and renew remaining slot revisions and discard restored retry receipts. Revoke restored sessions and invalidate restored invites and recovery codes whose current validity cannot be established. An older backup may contain a deleted account's invite in unredeemed form, so unverified pre-restore invites cannot stay active. Reopen only after reconciliation and verification. Restore-wide credential invalidation is separate from account-scoped live deletion.
5. Report bounded error categories and request IDs. Never log request bodies, credentials, snapshot contents, or journal payloads in HTTP or PostgreSQL diagnostics. Operational backup bytes remain protected and subject to their separately approved expiry schedule.

## Verification plan after approval

Use disposable local PostgreSQL 18.7 and synthetic accounts A and B. Verify all A-owned rows are gone, its prior bearer and recovery code fail, repeated deletion is safe, and B retains its live credentials, snapshot, and retry receipts. Prove both race orders for deletion versus upload, download, login, recovery redemption, and recovery-code rotation with controlled transaction interleavings. Verify the absent refresh route and stable errors without sensitive logging.

Create and verify a pre-deletion backup. Delete A, restore the older database without API traffic, and reconcile against the independently retained journal. Prove the older backup contained A, its snapshot and authorization material, and none becomes usable after replay. Verify B's data is intact and pre-restore credentials and revisions are handled under the restore-wide rules. Replay twice. Inject append failure, ambiguous append acknowledgement, interruption after append but before SQL commit, and journal loss, truncation and stale-copy recovery. Verify fail-closed behavior. Record commands and observed outcomes in [PLANS.md](../../PLANS.md#m6-market-ready-closed-pilot-apk).

**Execution evidence:** Read-only inspection of the backend and migration definitions. No route, migration, or journal was implemented. PostgreSQL integration tests and the older-backup restore drill have not run for M6.1. M4 physical release acceptance and M5 external staging and real-data gates retain their existing dispositions.
