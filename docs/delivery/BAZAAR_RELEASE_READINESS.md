# Cafe Bazaar production release readiness

**Status · OPEN.** Vehicle Ledger (دفتر خودرو) is intended for Cafe Bazaar distribution to Iranian drivers. The offline MVP development closeout and the focused signed RC5 upgrade and offline persistence check on the Redmi are complete. This document defines the evidence required for a future production release. It does not change M1–M7 acceptance history, the separate M4 physical gate, or the pause on server work. ## Vehicle Ledger production checklist

These are project release gates. Stage letters refer to the [product roadmap](ROADMAP.md#roadmap-from-rc5-to-cafe-bazaar). Keep each item **OPEN** or **DEFERRED** until the named evidence exists for the intended release and environment. An earlier fixture pass keeps its original scope.

| Stage | Gate | Evidence required |
|---|---|---|
| A | **OPEN · Persian RTL and visual identity** | Approved visual direction and reusable Compose Material 3 tokens and components. Actual signed-candidate or release-matched screenshots and visual regression evidence for supported layouts and approved appearances, including forms, overlays and state transitions. Compare to the approved reference screens and record intentional differences. |
| A/B | **OPEN · Accessibility and localization** | Physical TalkBack labels, ordering and focus, touch targets, contrast, actual system-wide 150% text with IME, and compact and wider layouts. Verify Persian digits, mixed-direction text, exact toman display and legacy-rial storage, Jalali month boundaries and Tehran dates. Preserve the documented Jalali range and visible fallback. |
| B | **OPEN · Offline correctness and upgrade** | Representative older and newer physical Android devices, including a supported low-API configuration. Verify offline install-to-cold-launch and real local logging, reopen and reminders. Exercise a populated signed upgrade, record signer and versions, and compare persisted records and exact report totals. The focused M4→RC5 Redmi pass covers its own fixture. The separate physical M3→M4 gate remains **DEFERRED / NOT VERIFIED**. |
| B | **OPEN · Local recovery** | Actual DocumentsUI export, restore into a separate empty ledger, export-time record equality, populated-target rejection, invalid-file and provider-write handling, and rollback after a failed insert. Verify that users can locate and retain the plaintext export and understand that it contains personal data and later edits require a new backup. |
| B | **OPEN · Reliability and performance** | On representative hardware, record cold launch, save-to-confirmation, History scrolling and monthly reporting with a documented large synthetic ledger. Agree a device, fixture size, measurement method and pass thresholds before running the gate. Record crash and ANR evidence, affected journeys and any accepted bounded residual risk. |
| C/D | **DEFERRED · Operational cloud recovery** | Approve provider, region, budget, operator and eligible access. Verify HTTPS and certificate renewal, private PostgreSQL, encryption at rest and encrypted off-host backups, least-privilege access, named key and credential custody, rotation, restore timing and backup recoverability. Test stalled or interrupted transfers, stale revisions, lost acknowledgements, replaced-device recovery and continued offline local logging. No automatic upload, sync or merge. |
| D | **DEFERRED · Security and privacy** | Review final Android permissions and exported components, app-private storage, backup exclusions, Keystore session protection, logging and network behavior. Review server access isolation, rate limits, abuse controls, audit and secret redaction. Approve the production cloud custody model, Persian consent and privacy disclosure, retention and purge deadlines, local erasure and separate cloud deletion. Verify revocation, account recovery, deletion without resurrection after an older backup restore, and documented incident response. |
| E | **OPEN · Pilot and Iranian connectivity** | With explicit real-data authorization, test the actual distribution and recovery paths on approved physical devices and at least two target Iranian mobile networks. Record DNS, TLS, download, session and transfer outcomes without relying on a VPN or provider location as reachability evidence. Record consent, recovery and support outcomes, with sanitized evidence and denominators. |
| F | **OPEN · Signing and release continuity** | Approve permanent application ID, signer model, key custodians, offline backup and recovery, credential separation, rotation and loss response. Decide how existing test-key installations keep their data, using verified in-place continuity where supported or an approved file-export/import transition. Verify the store-delivered artifact or split set, version code, signer, source provenance, hash where applicable, and real install and update path. The RC5 developer test key has no long-term production approval. |
| F | **OPEN · Persian help and listing** | Review install and upgrade help, account and local recovery instructions, data deletion and privacy policy, and a staffed support contact. Provide an approved icon, actual app screenshots, Persian description, category and release notes. Verify the assets and disclosures in the console against the product behavior and applicable rules. |
| G | **OPEN · Maintenance and incident handling** | Name the support and incident owner, escalation path, dependency and Android update cadence, monitored signals with privacy safeguards and release pause procedure. Rehearse restore and integrity checks before reopening affected services. For each update, exercise the populated signed upgrade path and document whether rollout can be stopped. Never assume a downgrade will preserve data. |

## Open cloud and signing decisions

- Security Option A is approved for limited-pilot design. The service can read snapshots. Production use requires a separate decision on plaintext access, operator controls, disclosure, provider and data and backup jurisdictions. Option B would require a separate architecture and recovery review. [ADR 0004](../architecture/ADR/0004-cloud-recovery-security.md)
- External staging, real-data processing and cloud operations remain unauthorized. The 90-day real-data snapshot proposal and proposed operational backup window remain unapproved. Account deletion, durable deletion records and post-restore reconciliation remain deferred. Approve custody, retention, purge, compromise response and responsibility before enabling the corresponding work. [M5 gates](../../PLANS.md#m5-operational-and-acceptance-gates) · [M6 decision record](M6_PILOT_DECISION.md)
- Establish the production application ID and signing decision before committing to a distribution artifact. Document the RC5 test lineage as historical evidence. Confirm signing continuity with the exact Bazaar workflow and supported Android versions before relying on rotation or a store-generated split package. [Existing signing evidence](ANDROID_RELEASE.md#android-offline-mvp-031-release-candidate)

Public release requires closed applicable gates, explicit product-owner authorization and the actual Bazaar review result. Submission readiness, store approval and public rollout are separate decisions.
