# Assumptions and evidence

| Item | Status | How to verify |
|---|---|---|
| Solo developer with Codex, signed Android APK, Kotlin and Compose, single module, Room | Approved baseline | Record implementation and device evidence at the milestone gates. |
| Driver can log in frequent, short sessions and benefits from monthly spending visibility | Unvalidated product assumption | Observe real entry, interview drivers about substitutes, and measure repeat logging in M7. |
| Ride-hailing drivers in one Tehran area are recruitable | Working hypothesis | Confirm a recruitment owner, channel, and area before pilot invitations. Use one alternative area if access is materially stronger. |
| Mobile devices can install the APK and reach cloud recovery | Unverified feasibility | Verify Android versions and actual install path. Test from target pilot networks before M6. |
| Local receipts and driver terminology match the chosen legacy-rial and toman display | Unverified presentation assumption | Review representative receipts and interview participants before finalizing M3 labels. |
| Explicit file and cloud recovery fit pilot needs | Technical recommendation within the approved baseline | Observe export and restore, verify that drivers can explain what is recoverable, and record demand for other workflows. |
| Businesses will consent and can maintain accurate public details | Unvalidated business assumption | Recruit 5–10 distinct businesses during M2–M4. Capture refusals, accuracy and correction ownership, and willingness to participate. |
| Engineering estimates reflect solo capacity | Provisional | Record actual development and debugging time in M1, including verification overhead. Re-estimate before M2. |
